> 编制：2026-08-24 ｜ 基于 v0.1.48 代码基线（main = e151115，冒烟 135 项全绿）
> 目标：① 建立可靠性/上限测试体系并测出打开文件数上限；② 大文件支持到 4GB 以下；③ 多窗口同时编辑；④ 多文档对比。

## 0. 现状与硬约束（决定方案的物理边界）

| # | 约束 | 出处 | 对方案的影响 |
|---|---|---|---|
| C1 | V8 字符串上限 ≈ 536,870,888 字符（2^29-24），结构化克隆单串同限 | V8/Chromium | 「整文件进编辑器可编辑」物理上限 ≈ 500MB（ASCII）；超过必须分层 |
| C2 | CodeMirror 6 文档全量驻留内存（doc ≈ 文本 2~3 倍），高度测量随行数劣化 | CM6 架构 | 4GB 全量加载 = 渲染进程 10GB+，不可行；超大文件只能窗口化查看 |
| C3 | `fs:write-file` 单串 IPC 传输；`saveNow` 用 `doc.toString()` 整串 | src/main/ipc.js / tabs.js | >64MB 保存需分块流式写协议 |
| C4 | 现有 chunked 模式（>4MB）滚动追加**无上限增长**，滚到底=全量进内存 | tabs.js P7 | 4GB 支持 = 追加模型改为「滑动窗口 + 驱逐」或只读查看器 |
| C5 | 主进程 IPC 绑定首窗口：filewatch `getAllWindows()[0]`、python/ai `getWindow()`、search 进度同 | filewatch.js / python.js / ai.js / search.js | 多窗口前置重构：全部改 `event.sender` 路由 |
| C6 | `renderTabs()` 在每次文档变更时**全量重建标签 DOM** | tabs.js updateListener | 多标签（100+）键入延迟瓶颈，需增量更新 |
| C7 | 会话恢复上限 50 标签（`paths.slice(0,50)`） | app.js restoreSession | 上限提升的前置优化点 |
| C8 | 全局搜索 worker 跳过 >10MB 文件（MAX_SEARCH_FILE_MB） | search-worker.js | 大文件搜索需流式扫描通道 |
| C9 | 大文件上限设置 max 1~2048MB | settings.js / app.js | 需提到 4096 并分层引导 |

**4GB 的务实口径**（本计划的核心设计决策）：
- **≤ EDIT_LIMIT（初值 64MB，由阶段一实测校准）**：现有 chunked 可编辑模式，全量补读后保存（现行为，路径不变）。
- **EDIT_LIMIT ~ VIEW_EDIT_LIMIT（初值 256MB）**：可编辑 chunked，保存改走分块流式写（C3），并提示大文件保存耗时。
- **VIEW_EDIT_LIMIT ~ 4GB**：**只读「大文件查看器」标签**——窗口化分段加载（保留前后各 ~8MB 滑窗，跳转按字节偏移/百分比定位），支持流式搜索定位；编辑需求通过「提取当前区域到新文件」满足。
- 理由：>256MB 的文本"全文编辑"在 CM6 上无合格体验（C2），业界同类（VS Code Large File、010 Editor）同为「查看 + 区域编辑」模型。

## 阶段一：可靠性用例 + 打开上限 + 大文件 4GB（建议版本 v0.1.49）

### 1A. 可靠性/压力测试体系（先测量，后优化）

| 用例 | 内容 | 验收 |
|---|---|---|
| stressTabs50/100/200 | 依次打开 N 个 100KB 文件，记录：总耗时、单次切换耗时、**有 100 标签时的键入延迟**（dispatch 100 次单字符测均耗时）、渲染进程堆内存（performance.memory.usedJSHeapSize） | 打开 100 标签 ≤ 15s；键入延迟 ≤ 50ms；切换 ≤ 300ms |
| stressTabInput | 100 标签下持续输入 30s（dirty 标记、自动保存关闭） | 无卡死、无标签丢失 |
| stressSession | 100 标签持久化 + 重启恢复（C7 上限提到 200） | 恢复后顺序/激活/pinned 一致 |
| stressLargeMulti | 同时打开 3×100MB chunked 标签：切换、滚动预读、分别保存 | 堆内存增量有界（<1.5GB）；保存内容校验无截断 |
| boundarySizes | **稀疏文件**边界矩阵（fs.truncate 秒建不占盘）：50MB / 512MB / 1GB / 2GB / 3.9GB / 4GB | 各档行为符合分层矩阵（打开/拒绝文案/查看器进入/预览禁用） |
| boundaryFind | 大文件内搜索（viewer 流式搜索通道） | 命中定位正确，超时可控 |

**前置优化（被压测逼出来的已知问题）**：
- O1 `renderTabs` 增量化：文档变更只更新 dirty 圆点/激活态，不再全量重建（C6）——预计 100 标签键入延迟从 O(N) DOM 重建降到 O(1)。
- O2 会话恢复上限 50 → 200，恢复并发度 3 → 6（大标签数下的启动时间）。
- 产出物：`docs/上限实测报告-0.1.49.md`（标签数×耗时×内存 表格，**明确回答"上限是打开多少个文件"**：硬上限=无，软上限=首个不达标指标出现的档位）。

### 1B. 大文件 4GB 分层支持

| 任务 | 内容 | 主要文件 |
|---|---|---|
| 1B-1 上限设置 | maxFileSizeMB 1~2048 → 1~4096，设置页文案分层说明 | settings.js / app.js / index.html |
| 1B-2 大文件查看器 | 新标签类型 kind='viewer-lg'：>VIEW_EDIT_LIMIT 进入；首窗口 ~8MB 流式解码；滚动到窗口边缘滑窗换页（驱逐远端内容）；字节偏移/百分比跳转；行号显示为窗口内相对行+字节定位 | tabs.js（新模块 viewer-lg.js 更佳） |
| 1B-3 IPC 通道 | `fs:read-file-window`（返回窗口字节+窗口字节起止+总大小；复用 read-file-range 的循环读满逻辑）；只读标签禁止编辑（readOnly Compartment） | ipc.js / preload.js |
| 1B-4 大文件搜索 | search-worker 增加流式扫描：>10MB 文本文件按 8MB 块流读行扫描（上限 4GB，进度事件已有），命中返回字节偏移+行号（近似行号：按块内换行累计） | search-worker.js / search.js |
| 1B-5 跳转联动 | 全局搜索命中大文件 → 打开 viewer-lg 并定位到字节偏移窗口 | globalsearch.js / tabs.js |
| 1B-6 区域提取编辑 | viewer-lg 内「提取此区域到新文件」（选区或当前窗口 → 另存新文件正常编辑） | viewer-lg.js / ipc.js |
| 1B-7 分块流式写 | `fs:write-stream-open/append/close` 三通道协议；saveNow 对 >64MB 走流式（分 16MB 块）；markSelfWrite 在 close 时记录 | ipc.js / security.js / filewatch.js / preload.js / tabs.js |
| 1B-8 预览/AI 路径防护 | viewer-lg 标签禁用 markdown 预览渲染与 AI 读全文（返回提示），避免整串提取 | preview.js / app.js executeAiTool |

**验收（新增冒烟约 8~10 项）**：3.9GB 稀疏文件可打开查看器并滑窗滚动/跳转；2GB 内可流式搜索定位；100MB 可编辑+流式保存往返校验（读回哈希一致）；4GB 恒拒（超出"4GB 以下"口径，文案引导）。

工作量：1A 1~1.5 人日；1B 2~3 人日。风险：滑窗换页的滚动位置保持（CM 高度估算跳变）→ 用固定行高估算+跳转对话框定位规避。

## 阶段二：多窗口同时编辑（建议版本 v0.1.50）

### 2A. 主进程 IPC 去首窗口化（前置重构，C5）

| 任务 | 内容 |
|---|---|
| 2A-1 | filewatch.js：watchers 注册带 windowId；`file-changed` 只发给注册窗口（`BrowserWindow.fromWebContents`/存储的 win 引用，销毁即注销） |
| 2A-2 | python.js：输出/退出/启动事件按发起窗口路由（batcher 持有 win）；kill 全局仍按发起窗口 |
| 2A-3 | search.js：进度/结果只回请求窗口（invoke 天然按 sender 返回 ✓，仅 progress 事件需带 windowId） |
| 2A-4 | ai.js：tool-call/chunk/done 按 sender 路由 |
| 2A-5 | dialog:confirm / clipboard 等 getWindow() 通道全部改 `BrowserWindow.fromWebContents(event.sender)` |

### 2B. 窗口管理

| 任务 | 内容 |
|---|---|
| 2B-1 | 「新建窗口」入口：菜单 + Ctrl+Shift+N；main.js 维护窗口列表；`window-all-closed` 语义不变（全关才退出）；`activate` 处理 |
| 2B-2 | 单实例：`requestSingleInstanceLock`，二次启动 `second-instance` → 在已有实例开新窗口（替代当前双开进程的设置互写风险） |
| 2B-3 | 每窗口独立状态：rootDir/标签/面板各自隔离（渲染端天然每窗口独立 JS 上下文，加载同一 index.html 即可）；`window.__app` 每窗口各自暴露（smoke 绑定主窗口不受影响） |
| 2B-4 | 会话策略：lastSession 按"最后获得焦点的窗口"整体保存（v1 简化；重启恢复为单窗口会话）；dirArg 命令行目录 → 开新窗口 |
| 2B-5 | 跨窗口联动：设置/主题变更经主进程 `settings:changed` 广播所有窗口即时同步；Python 运行互斥策略（全局单实例，第二窗口运行时提示占用——沿用现有互斥语义） |
| 2B-6 | 同文件跨窗口冲突（两窗口编辑同一文件互视为外部修改）：v1 策略=允许 + 焦点切换时提示风险对话框（「该文件已在另一窗口打开并修改」）；登记主进程跨窗口打开表 |

**验收（新增冒烟约 6~8 项，主进程开第二 BrowserWindow 驱动）**：双窗口各自打开不同目录与文件；A 窗口外部修改事件不串到 B；Python 输出回到发起窗口；主题切换双窗同步；同文件双窗提示；关一窗另一窗正常。

工作量：2~3 人日。风险：filewatch 窗口销毁竞态（注销时机）→ will-quit/closed 双钩子清理；smoke 需要新 harness 支持第二窗口断言。

## 阶段三：多文档对比（建议版本 v0.1.51，或并入 v0.2.0 正式版）

| 任务 | 内容 |
|---|---|
| 3A 依赖 | 引入 `diff`（jsdiff，行级 diffLines + 词级 diffWords 内联高亮；体积小、纯 JS） |
| 3B 入口 | ① 工具栏「对比」按钮：当前标签 ↔ 另一打开标签/剪贴板/磁盘版本（未保存改动）；② 文件树右键「与此文件对比」需二选交互（v1 用对比面板内文件选择器，树多选后置） |
| 3C UI | 对比标签页 kind='diff'（独立内容区，可同时开多个对比）：左右双栏、同步滚动、行级增/删/改 + 词级内联高亮、变更块 ↑↓ 导航、统计徽标（+N −M 行）、等宽字体对齐 |
| 3D 大文件 | diff 输入上限默认 20MB/侧（超出提示拒绝或截断前 N 万行——jsdiff O(ND) 内存/耗时不可控）；viewer-lg 大文件对比列为后置 |
| 3E 只读 | diff 标签只读；「交换左右」「导出对比报告为 Markdown」两个轻量增值动作 |
| 3F 集成 | 会话持久化跳过 diff 标签（临时视图）；关闭确认不需要 |

**验收（新增冒烟 5~6 项）**：两文件 diff 块数/统计正确；导航跳转；未保存改动对比与磁盘版本一致；超限拒绝；diff 标签不入会话。

工作量：1.5~2 人日。风险：双栏同步滚动手感（按变更块对齐）→ v1 按行号比例同步，v2 精确对齐。

## 全局风险清单

1. **分块流式写**与自写识别（filewatch 宽限窗口）的交互：close 时统一 markSelfWrite，中途不触发。
2. **多窗口 + smoke**：现有 135 项绑单窗口，需保证第二窗口用例不影响既有用例隔离（独立测试目录）。
3. **jsdiff 引入**需过 CSP/打包检查（纯浏览器库，预期无障碍）。
4. **viewer-lg 行号语义**（窗口相对行 vs 全文件绝对行）需在 UI 文案明确，避免误读。
5. 大文件测试全部使用**稀疏文件**（fs.truncate），不实际占用磁盘；但读取时是真实零字节流，编码检测按 latin1 处理即可。
6. 每阶段 CHANGELOG/README/AGENTS.md（冒烟计数）同步更新。

## 待用户确认的决策点

- D1：>256MB 只读查看器 + 区域提取编辑的分层口径（vs 强行全文可编辑——不可行，理由 C1/C2）。
- D2：多窗口同文件冲突 v1 采用「允许 + 提示」（vs 第二窗口只读打开）。
- D3：三阶段拆三版发布（推荐）vs 合并为 v0.2.0 一次发布。
- D4：对比功能 v1 为双栏只读 diff（合并/三方对比后置）。

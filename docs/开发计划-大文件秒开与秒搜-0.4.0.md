## 1. 现状与瓶颈（代码定位）

| 能力 | 现状实现 | 为什么慢 |
|---|---|---|
| 4MB–256MB | 分段模式：2MB 一段追加进 CodeMirror（`tabs.js` `openChunkedTab`/`loadNextChunk`） | 最终把全文塞进 CM + V8 单字符串（上限 ≈5.36 亿字符）→ 上百 MB 已是极限 |
| 256MB–1GB | **滑窗查看器**（`kind='viewer-lg'`）：`VIEWER_WINDOW=8MB`、`VIEWER_STEP=6MB`，`slideViewer`/`viewerJump` 一页页换窗，`loadViewerWindow` 整窗替换文档 | 8MB 窗 × 约 128 页（1GB）；滚动到边界只能"翻页"，无法把滚动条拖到任意位置 |
| **>1GB** | **虚拟滚动查看器**（`kind='huge'`，`src/renderer/hugeview.js`）：只渲染视口行，一屏一次 IPC | 已解决连续滚动（B 已交付）；**本轮只读**，编辑面尚不存在（D 第二/三步） |
| 大文件搜索 | `search-worker.js` `scanStream`：8MB 块 + 流式解码 + **逐行 `toLowerCase().indexOf()`**（JS 层） | 纯 JS 逐字符扫描；2GB ≈ 数十秒；结果上限 3000，无行号→字节偏移直跳（只能靠 `fs:find-line-offset` 再扫一遍） |
| 定位跳转 | `viewerJump` 支持 % / 字节偏移；全局搜索命中大文件靠 `fs:find-line-offset` 流式数换行 | 每次跳转都要重新扫描统计换行，O(文件大小) |

**结论**：问题不在"读得慢"，而在**缺少行索引 + 缺少虚拟滚动**。有了稀疏行索引，任意位置都能 O(1) 定位；有了虚拟滚动，滚动条可以像小文件一样连续拖。


## 3. 稀疏行索引（核心基础设施）

- **内容**：每 K 行（默认 K=1000）记录一次「行首字节偏移」，外加总行数、最长行长度、是否含 NUL。
  - 2000 万行 → 2 万条目 → 约 160 KB 内存（`Float64Array`）。
- **构建**：主进程（或 utilityProcess）流式读 8MB 块，扫描 `0x0A` 字节计数（`Buffer.indexOf` 循环，原生速度），增量解码只为确定编码，不逐行做字符串操作。
  - 3.9GB 冷扫 ≈ 一次顺序读（NVMe 约 3–8s；机械盘更久）→ **后台线程 + 进度**，不阻塞查看。
- **侧车缓存**：`userData/lineidx/<sha1(path|size|mtimeMs)>.idx`，二次打开同一文件毫秒级命中；文件被外部修改（size/mtime 变化）自动失效。
- **两阶段显示**：索引未就绪时，用前 64MB 的平均行长**估算**总行数撑起滚动条（标注「索引建立中 xx%」），就绪后校正行数与高度。
- **行号 → 字节偏移**：`offset(line) = idx[line / K]` + 从该处向后跳 `line % K` 个换行（最多 K 个）。这同时替掉了现有 `fs:find-line-offset` 的全量扫描。

## 4. 虚拟滚动查看器（替代分页）

- **滚动容器**：总高 = 总行数 × 行高；只渲染视口 ± 1 屏的行（绝对定位 / 或 spacer + 分段渲染）。
- **取数**：滚动 → 目标行号 → 索引定位字节偏移 → `huge:lines`（主进程 LRU 缓存 8MB 对齐块，命中即回）→ 增量解码 → 填 DOM。
- **体验**：滚动条可拖到任意位置；`Ctrl+Home/End`、`Ctrl+G 行号`、`%`/字节偏移跳转都变成 O(1) 定位；翻页按钮保留但不再是唯一手段。
- **超长行保护**：单行 > 64KB 时按视口宽度截断显示 + 「展开此行」（沿用现有 `CELL_MAX_CHARS` 思路）；巨型单行文件退化为"按字节分块 + 行号近似"模式并明确提示。
- **二进制守卫**：沿用现有 NUL 检测（`overlay.js` `checkEditable`：含 NUL → `editable:false` + 只读 + 禁用编辑）。
- **DOM 代价**：每屏约 50–80 行 × 若干 span，远低于现在"整窗 8MB 进 CM"的开销；内存目标 < 300MB（含块缓存）。

## 5. 快速搜索（分片并行 + 原生匹配）

- **匹配**：在 8MB `Buffer` 上用原生 `buf.indexOf(pattern)` 定位（比逐行 JS 快一个数量级）；跨块命中保留 `pattern.length - 1` 字节重叠。
- **编码**：沿用「首块严格 UTF-8 → GBK」探测；UTF-8 直接匹配 UTF-8 字节；GBK 文件把查询串转 GBK 字节；纯 ASCII 查询两者等价。
- **行号**：命中偏移 → 用行索引二分得到行号（不需要重扫），行文本从块内切片（截断 1000 字符，沿用现有上限）。
- **并行**：按 CPU 核数（上限 8）把文件切成 N 段，每段一个 `utilityProcess`（复用 `search-worker.js` 机制）→ 2GB ASCII 关键词目标 < 3s。**当前单进程原生快路径已达标（89ms / 173MB），分片并行降级为可选加速项。**
- **交互**：命中列表虚拟滚动 + 进度条 + 取消（复用 `search:progress`/`search:cancel`）；点击命中 → 查看器直接 seek 到该行（O(1)）；上限默认 1 万条（远超现有 3000）。
- **小文件**：≤10MB 仍走现有整读路径，不变。

## 6. 编辑策略（「临时缓冲编辑」，EmEditor 式）

**模型：按行分块的写时复制（block-CoW + 前缀和）** —— 4GB 文件按 ~10 万行一块（约 8MB）切成几百到几千块，块数少到可以用**普通数组 + 前缀和**精确定位（无需 Fenwick/绳树）：

- **文档 = 块序列**，每块记录 `{来源: 原文件区间 | overlay 缓冲区, 行数, 字节数}`；总行数 = 前缀和 → 行号 ↔ (块, 块内行) 映射 O(log n)（二分）或 O(1)（前缀和+二分）。
- **编辑**：只把受影响的块标脏并把新文本写入 `userData/overlay/<sha1>.tmp`（追加写，带块偏移表）；跨块插入/删除按经典块分裂/合并处理；改完只需重建前缀和（几百项，微秒级）。未改动的块**始终留在原文件里，从不读入内存**。
- **读取**：视口需要哪些行 → 定位到块 → 脏块从 overlay 读、干净块从原文件按偏移 `read-range`（沿用现有 LRU 块缓存）。
- **保存（安全第一）**：流式把块序列顺序写出到 `<file>.mh-save.tmp` → 校验字节数 → 原子 `rename` 覆盖（与现有 `fs:splice-file` 同款策略）。4GB 约 20–60s，带进度条与可取消；**不做就地增量改写**（行数变化会移动后续全部数据，全量重写是唯一无风险路径）。
- **自动保存**：大文件（**指 >256MB 的只读查看器/虚拟滚动两档**；本轮只读故无实际影响，D 开编辑后生效）默认**关闭自动保存**，只响应 Ctrl+S 与关闭前确认；设置里可开"保存前自动备份"。overlay 常驻磁盘 → 崩溃后可提示"恢复未保存的编辑"。
- **撤销**：块级操作栈（`UNDO_LIMIT` 默认 200 步，仅保存脏块文本引用），内存占用与编辑量成正比。
- **边界**：二进制文件（含 NUL）仍禁止编辑；无换行/超长行退化为"按视口分块 + 行号近似"并明确提示。
- 现有「区域编辑 + `fs:splice-file` 写回」保留为兜底入口，与新编辑模型并存（互斥：进入临时缓冲编辑后不再用区域写回）。

**不做**：像 EmEditor 那样把 4GB 全量载入内存（我们不复制其内存模型，只复制其交互体验：连续滚动 + 任意位置编辑 + 快速搜索）。

### 6.2 单例与所有权（第二步必须落成代码，否则会被 0.5.0 Phase 3 推翻）

- **路径 → 单例 doc**：`overlay-ipc.js` 内维护 `Map<resolvedPath, doc>`。`overlay.js` 自身**没有**该注册表（只有 `st.chunks`/`st.cache` 两个内部 `Map`，`src/main/overlay.js:507-508`），`src/main/overlay.js:313` 的注释把「同一 key 串行」推给调用方 —— 单例语义是 `overlay-ipc` 的责任。
- **owner 校验**：`ownerWebContentsId` 只是**记录**（`src/main/overlay.js:502/1203/1233`），模块内不做鉴权。`overlay-ipc` 必须校验「发起的 webContents 是否为该 doc 的 owner」，非 owner 一律拒绝写操作。
- **多窗口语义**：沿用 `src/main/filewatch.js:151-155` 的 `file-shared-open` 只读语义（后被打开的窗口转只读），**不允许**两个窗口各持一个 overlay 互相覆盖（`docs/交接-会话纪要.md:56` 已把它列为第二步必测项）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 首次索引耗时（机械盘更慢） | 后台 + 进度 + 估算高度先可滚动；缓存到磁盘；可在设置里关"预建索引" |
| 超长行 / 无换行文件（如 4GB 单行日志） | 超长行截断显示 + 「展开」；无换行时退化为按字节分块视图并提示 |
| 编码判定错误（GBK/UTF-8 混合） | 沿用现有首块严格探测 + 用户可强制指定编码（新增设置项）。注意 `overlay.js` `checkEditable` **拒绝 GBK 大文件编辑**（Node 无 GBK 编码器，保存会产生混合编码），这是有意为之 |
| 磁盘缓存陈旧 | key = path+size+mtime；文件变更即失效并后台重建（`src/main/lineindex.js:56-60`） |
| 并行搜索 IO 争用 | 分片数按核数上限 8，且读块大小 8MB；提供"低速模式"（单线程）。当前单进程已达标，不阻塞 |
| **`fs.watch` 在原子 rename 后失效** | `src/main/filewatch.js:142` 用 `fs.watch(filePath)` 持句柄，而 `src/main/overlay.js:1069` 用 `fsp.rename(tmp, target)` 原子替换目标文件 → 旧句柄可能指向被替换的 inode。**第二步必须在真实窗口实测**；若确认失效，保存成功后无条件重挂 watch（`unwatchFile` + `watchFile`） |
| 保存后目录级事件误报 | 保存会触发目录 watch 事件 → 可能被当成"外部修改"。对策：`markSelfWrite` 宽限窗口（`filewatch.js:160`）+ 保存路径显式 `markSelfWrite(newMtime)`；真实窗口实测 |
| 多窗口同文件各持 overlay 互相覆盖 | 第二步按 §6.2「路径→单例 doc」持有并复用 `file-shared-open` 只读语义 |

### 13.5 实测语义修正（`scripts/overlay-test.js` 取证 —— **下次写 overlay 相关代码前必读**）

> 这一节修正的是本计划 §6 与任务书里的**错误假设**，都有一手实测支撑。

† 基线单键延迟用 `applyEditForTest` 量（主进程编辑 + 状态同步 + 光标行重取 + 重画，等价于一次按键的完整串行链）；现在用真实 keydown 量「按下 → 视口回显」。

### 14.2 四个根因与对策（按收益排序）
1. **首屏等整份行索引（2–4.5s）** —— `lineindex.scan` 每读完一个 8MB 块就把「已扫描前缀」的行首表发布到 `partialIndexes`（同一份数组引用，只读）；`readLines` 不再 `getIndex` 阻塞，而是：完整索引 → 用完整表；构建中 → 用前缀（行号精确）；未扫到 → 立刻返回 `pending`；第 1 行 → 直接读文件头。`hugeview` 去掉「索引未就绪不取数」的闸门，改画进度占位 + 进度事件重试，并修正 `getState().indexed` 为「索引已画出」。
2. **搜索锚点落在空格上（5GB 20s）** —— `nativeMatchesCI` 的 `LETTER_FREQ` 把非字母记 0，查询里的空格/数字被当成「最稀有」。换成 0x00–0xFF 的真实频率表（空格 180‰、字母按语料、数字/标点 0.2–9‰）后 20.2s → 4.6s（node 单线程实测）。
3. **单线程搜索（4.6s）** —— >128MB 的纯 ASCII 查询按字节分 N 片（核数-1，上限 8）给 `worker_threads`，行号用「各片换行数前缀和 + 片内偏移」；跨片命中用 needle-1 字节重叠。**关键坑**：分片线程里每 8MB 块 `allocUnsafe + Buffer.concat` 在 Electron 的 worker_threads 中奇慢（640MB/片 2.5s+，node 24 同代码 0.6s）——改「一片一个复用缓冲 + 尾部搬移」后 0.63s/片，5GB 全量 0.70s。
4. **编辑物化整块 10 万行（12.8MB/键）** —— `spliceLines` 物化前按 1000 行稀疏档把触及的 file 块切开（边界取自 `base.starts`，零 IO；块新增 `baseLine`），单键只处理 ≤128KB；回执带撤销栈状态，渲染端快路径去掉每键的 `huge:doc-state` / `huge:doc-line`。

### 14.4 仍挂账（下一轮候选）

- **索引建立中跳到未扫描区域** → 仍是进度占位（0.2–1.4s 等扫描推进）。若要做成「任意位置立刻出字」，需按字节比例读 + 近似行号（`≈` 标注），索引就绪后校正 —— 会动 `hugeview` 的行号口径，需同步改冒烟断言。
- **非 ASCII 大文件查询**（中文关键词）仍走单线程增量解码，5GB 量级预计数十秒；分片需要每片独立编码探测 + 行号前缀和，改造面比 ASCII 大。
- **保存期间**同文档的 `huge:doc-lines` 被 `withDocLock` 排队（状态栏有进度，但视口冻结 5–10s）。可选：保存前快照块表、读路径改走快照。
- **`meta()` 未持久化 `baseLine`**：崩溃恢复出来的文档首轮编辑仍会物化整块（正确但慢），下次保存/重建索引后恢复。
- **in-view Ctrl+F**：huge 视图内仍明确提示「当前视图不支持文件内查找 —— 可用 Ctrl+G / Ctrl+Shift+F」（v0.8.0 已加文案，不是静默 0 命中）。

### 14.5 追加轮（同日，用户点名两项）：「自动换行」+ 删除悬浮操作条（顺带修滚动锚点）

- **自动换行**（状态条「↵ 自动换行」，应用级 `wordWrap`）：行号只在逻辑行首行；行高实测后逐行累计定位；换行时滚动条末尾补一屏，保证最后一行可滚到视口顶部；单行最多折 40 个视觉行（约 800px）后截断提示；渲染窗按上次实测行高自适应（1MB/行夹具：180 行/屏 → 28 行/屏）。**已闭环到设置**：状态条按钮回写应用级 `wordWrap`（`app.js` 统一落盘 + 同步 CodeMirror + 其它已开的大文件视图；`huge.setWrapPreference()` 供外部同步、不再回调，避免环），`bigperf.wrapToggle` 断言了开关与设置落盘的双向一致（`persistedOff/persistedOn`）。
- **删除 `#viewer-bar`**：分页查看器（viewer-lg）遗留的悬浮操作条（⏪/位置/⏩/📍跳转/✏️启用区域编辑/📤提取为新文件）整条 DOM + 按钮事件 + ID + CSS 全部移除；`viewer-lg` 的分页/区域编辑代码保留（生产路径不可达、不再有 UI 入口）。冒烟 `viewerBarBelow`（图片弹窗操作条）不受影响。
- **滚动锚点修正（v0.8.0 遗留缺陷）**：旧 `translateY(scrollTop)` 让屏幕内容恒定落后滚动位置 `(first-from)` 行（2 屏）—— `gotoLine(20000000)` 后 `firstLine=20000002` 但 DOM 顶部是 19999930。改为 `translateY = scrollTop − offsetFirst − frac`；`.huge-sizer{overflow:hidden}` 保证换行后块高不撑大 `scrollHeight`。连带修正：文件末尾几十行可达、无选区 Ctrl+C 复制的是屏顶行、键入落点即所见、状态栏「行 X」改用 `firstLine`、索引就绪后状态栏刷新（此前一直停在「共 1 行（索引建立中）」）。
- **新增回归断言**：`npm run bigperf` 的 jump 用例比对「DOM 视口顶部行号 == firstLine」；新增 `wrapToggle` 用例（1GB 长行夹具：换行行高 > 行高、关闭后 == 20、DOM 顶部行号 == firstLine）。
- 验收：`npm run smoke` 244 全绿；`npm run bigperf` **BIGPERF_DONE fails=0**（5GB 首屏 22–57ms、搜索 0.75–0.99s、保存 5.1s、单键 11ms；10GB 首屏 22ms、搜索 0.75s、保存 9.9s；wrapToggle 行高 180↔20）。
